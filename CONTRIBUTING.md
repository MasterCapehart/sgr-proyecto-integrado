# Trabajo en equipo

## Flujo

1. Crear o tomar una tarea de GitHub Issues y asignarse como responsable.
2. Actualizar la copia local de `main` antes de crear una rama.
3. Crear una rama por tarea: `feat/login-roles`, `feat/registro-actividades` o `fix/validacion-evidencias`.
4. Hacer commits pequeños con mensajes claros.
5. Publicar la rama y abrir un pull request hacia `main`.
6. Solicitar revisión de otro integrante y resolver las observaciones.
7. Integrar cuando la revisión y las comprobaciones sean satisfactorias, y eliminar la rama terminada.

No trabajar directamente sobre `main`. La revisión es un acuerdo del equipo; no está impuesta técnicamente por esta estructura inicial.

## Coordinación

- Acordar los datos de entrada y salida de la API antes de implementar funcionalidades compartidas.
- Coordinar cambios al modelo de datos y versionar las migraciones.
- Incluir en cada cambio las instrucciones necesarias para que los demás puedan ejecutarlo.
- Usar datos ficticios para desarrollo y pruebas.
- Mantener los documentos vigentes en `docs/`.

## Autoría

Usar la identidad Git personal de cada integrante. No añadir atribuciones, coautorías ni firmas de asistentes a los mensajes de commit.
